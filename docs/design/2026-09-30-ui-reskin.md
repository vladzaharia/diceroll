## 1. Visual direction

### 1.1 Decision: "Night navy + wood"
Four directions were mocked on the live board (`00_direction_options.png`):
- A: parchment + wood
- B: navy + gold frame
- C: slate
- D: navy + wood

**D was chosen**, for these reasons:
- **It suits the world.** The KayKit board is built from chunky wooden tile plinths on warm, dusky biomes. The pack's `Nailed` darkbrown frame reads as the same wood, so modals look like part of the board game rather than an app sheet. B's orange frame fought the orange PRIMARY buttons, and C looked cold.
- **Readability and cost.** Surfaces stay navy, so the whole text palette (`TEXT`, `TEXT_DIM`, gold accents) and the 40-odd hand-built screens keep working. A (cream parchment) looked lovely, but it flips every label colour in every screen and makes the dark 3D board behind a modal feel heavy.
- **Pack fidelity.** Buttons, chips, bars and widgets use the pack's native colour families unchanged: bright, chunky, 3D-lipped. That is where the "cartoony" consistency comes from. Only the large surfaces are navy.

### 1.2 Families
| Role | Pack family | Why |
|---|---|---|
| Text buttons | `UI/Buttons/3D/Square/*/button-square-3d-2.5-*` | the 3D lip matches today's GameButton depth-and-press feel; square corners hold long labels better than pills |
| Icon-only buttons | `UI/Buttons/3D/Round/*/button-round-3d-2.5-*` sliced to a square | the `-1` art is oval (54/64 wide, per plan a, R4). The 2.5 art sliced to w=h gives a true circle |
| Chips, pills, HUD counters, tabs, badges | `UI/Buttons/Flat/Round/*/button-round-flat-2.5-*` | flat, so it does not compete with real buttons |
| Modal frame | `UI/Frames/Nailed/9. Brown/frame-nailed-darkbrown-dark.svg` | wood with nails. Plain `darkbrown` reads rust-orange against navy; `-dark` reads as wood (rendered comparison in `mock_plan_c_decisions.png`, lead call on plan c) |
| Modal title | a **plaque**: `UI/Buttons/3D/Square/3. Yellow/button-square-3d-2.5-yellow-regular_standard.svg` (not a ribbon) | the pack has no ribbon art. A yellow 3D plaque overlapping the frame top reads as a sign nailed to the board |
| Cards | `UI/Containers/3D/0. White/container-3d-white.svg` tinted navy | a chunky lip without a second frame colour |
| Selected / accent card | card + `UI/Frames/Thin/*` overlay | |
| Tooltips, toasts, callouts | `UI/Containers/Flat/0. White` × INK + `UI/Frames/Thin/9. Brown/frame-thin-darkbrown.svg` | a thin wooden rim, like the modal but lighter |
| Insets / wells | `UI/Containers/Flat/0. White` × INK, alpha .55 | |
| Bars | `UI/Bars/{Wide,Regular,Thin}` | grey-darker track plus a coloured fill |
| Widgets | `UI/Widgets/{Checkboxes,Radio Buttons,Toggles}`, `UI/Bars/Handles/handle-round.svg`, `UI/Widgets/Cursor/cursor-focus.svg` | |

Other frames have narrow, named uses. This keeps one visual language (lead calls on plans c and d).
- **Pointed** (× affix/danger colour, scale 0.6): enemy and danger surfaces only (encounter cards, boss card).
- **Ornate:** only as a thin gold overlay (× BOSS, scale 0.45) on boss-tier cards (boss passives, boss unlocks).
- **Inset:** only the small `well` behind 3D thumbnails (plan d). Panel insets are flat containers, not the Inset frame.
- **Basic and Square Corners:** not used.

### 1.3 Colour mapping and recolouring rules
1. **Use the native pack family when the role matches.** No tinting in that case.

   | Role | Family | Pack face (normal / hover) |
   |---|---|---|
   | Primary / gold | `3. Yellow` `yellow-regular` | `#fdaf18` / `#fec92b` |
   | Secondary / info / Block | `6. Blue` `blue-regular` | `#37b9ff` / `#96dbff` |
   | Danger / HP / NEW | `2. Red` `red-regular` | `#f5535c` / `#ff7a6e` |
   | Success / heal / ON | `4. Green` `green-regular` | `#8cc936` / `#acdc58` |
   | XP / epic / Sigils | `7. Purple` `purple-regular` | `#c442ff` |
   | Ghost / HUD pills / tracks | `1. Grey` `grey-darker` | `#324652` / `#476475` |
   | Disabled | `1. Grey` `grey-regular` | `#7b97a6` |
   | Wood | `9. Brown` `darkbrown` | `#6e1e0d`, `#420b04`, `#9c3d29` |

2. **Palette-only colours use the `0. White` asset with a baked multiply tint** (foundation `UiSvg.recolor`, crisp at every density). This covers:
   - navy surfaces (NAVY, NAVY_2, NAVY_3, INK)
   - class accents (`UiPalette.CLASS`)
   - rarity rims (`RARITY`, `PASSIVE_RARITY`)
   - biome colours (`BIOME`)
   - die-kind colours (`KIND`)

   The tinted white art keeps the pack's 3-tone look: face ≈ 1.0×, lip ≈ 0.83×, outline ≈ 0.4× the tint.
3. **`modulate` is used for alpha only** (scrims, locked cards at .7, insets at .55). Never modulate a whole Control: that also tints its label and icon.
4. **Labels on button faces are ink.** Measured WCAG contrast of `TEXT_DARK #2a1606` on every face, in every state:

   | Face | normal | hover | pressed |
   |---|---|---|---|
   | yellow-regular | 9.3 | 11.2 | 9.3 |
   | blue-regular | 7.9 | 11.4 | 7.9 |
   | red-regular | 5.2 | 6.8 | 5.2 |
   | green-regular | 8.7 | 10.8 | 8.7 |
   | purple-regular (chips only) | 4.6 | 6.0 | |
   | grey-regular (disabled) | 5.6 | | |

   All states pass 4.5:1. White labels failed on every bright face (1.5 to 3.3:1). The only exception is **ghost** (`grey-darker`): it uses `TEXT #fbf3e2` at 9.8 / 6.3 (hover) / 9.8. There is no text outline or shadow on ink labels; the pack's art does not use them.

### 1.4 UiPalette changes
- Existing constants keep their names and values, so screens do not break.
- Add pack tokens, used by builders and by `palette:` tints in `icon_map.json`:
  ```
  WOOD := #6e1e0d   WOOD_DARK := #420b04   WOOD_LIGHT := #9c3d29
  PACK_YELLOW := #fdaf18   PACK_BLUE := #37b9ff   PACK_RED := #f5535c
  PACK_GREEN := #8cc936   PACK_PURPLE := #c442ff   SLATE := #324652   SLATE_2 := #476475
  INK_LABEL := TEXT_DARK   # label ink on every bright face
  ```
- Redirect `PRIMARY` to `#fdaf18` and `DANGER` to `#f5535c`, so the few hand-drawn things that still read them match the art.
- `SECONDARY` / `SECONDARY_DARK` stay navy. They are used as surface colours in several screens. The **button** secondary is the blue pack family, which is not a palette constant.
- `GOLD`, `TEXT*`, `HP`, `BLOCK`, `XP`, `KIND`, `CLASS`, `BIOME` and the rarity constants are unchanged.

### 1.5 Fonts
Unchanged: Lilita One (display, buttons, plaques, numbers) and Fredoka (body).

## 2. Component map

Measured slices come from rasterising each SVG at 4x and finding where rows and columns stop changing (script: `scratchpad/nine.py`). They agree with plan (a) §2a.

Two rules apply everywhere:
- **Full-radius art must keep a 1-unit stretch band** (plan a R6). Pills, toggles and Thin bars therefore use T+B = height − 1.
- **Scale** is px per viewBox unit. Every texture is a vector rasterised by the foundation (`UiSvg` / DPITexture) at the viewport's oversampling, so no PNG is ever used.

## 3. Scaling rules (phone vs desktop)
- The canvas is 720x1280-based `expand`: phones are about 720 logical wide in portrait, and desktops about 1280 tall. All numbers above are logical px and hold for both.
- **Touch targets:**
  - 88 px minimum for every primary action. It is 44 pt at the 90% UI size, so do not go lower.
  - Controls drawn smaller than 88 px get an 88 px hit rect.
- **Desktop only:** hover art, focus art, tooltips on hover, scrollbars, the hover keycap and the Settings → Controls list (§6).
- **Frame scale** is 1.0 everywhere. A 1.25 frame on desktop at 1080p or taller is allowed but not required.
- **Density:** the foundation re-rasterises SVGs at the viewport oversampling (stretch × content scale × DPI). Check for slice seams at 1366x768 and at 125% zoom.
- **Landscape phone (874x402):** modals shrink or scroll earlier because the chrome is taller. Verify `ui_draft`, `ui_shop` and `ui_settings` on `iphone17_land` and `duo_outer`.

### 3.1 Containment (hard rule, user requirement)
**Nothing extends beyond its container.** The user's original "spillover" complaint turned out to be about the huge bottom exit button (§3.2). These rules are kept as layout hygiene.

1. **Everything stays inside.** Badges, NEW dots, chips, tooltips, toasts, hover keycaps, selection rims and focus rings all stay fully inside their panel's content box. Screen-level elements (toasts, tooltips, HUD) stay fully inside the device safe area.
2. **Explicit exemption: the modal title plaque and the corner ×.** The plaque overlaps the frame top by half its height, and the × sits on the top-right corner (§2.4). Both must stay on-screen and inside the safe area, and must not overlap each other or any content.
4. **NEW dots and count badges** sit inside their card or tag bounds, inset 8 px from the corner. Nothing is hung off a corner. Station-tag counts (plan d) sit inside the tag's right end.
5. **No clipping or overflow at any device in the matrix:**
   - the 720-wide phone canvas and Duo outer
   - 1366x768
   - zoom 125–150%
   - iPhone landscape

   This covers text and controls. When space runs out:
   - labels shrink to their minimum font, then wrap, then truncate with an ellipsis;
   - rows wrap to a second line;
   - modal bodies scroll.

   A control is never pushed outside its container.
6. **Hover keycaps** sit inside the button's visible face (§6). Round and icon-only buttons show no keycap: the shortcut goes in their tooltip.
7. **Tooltips and toasts** are clamped to the safe area. A tooltip that would cross a screen edge flips to the other side of its anchor.

### 3.2 One exit (hard rule, user requirement)
See `mock_one_exit.png`.

1. **Exactly one dismiss control per modal: the header ×.**
   - Esc and tapping the dimmed backdrop also dismiss, where that is safe.
   - No full-width or large bottom button may exist only to close, go back or say "Done".
   - Settings apply live, so they need no Done.
2. **Bottom action rows are only for real decisions:** TAKE, BUY, CRAFT, START RUN, TO CAMP, REROLL / RESTOCK, CONFIRM.
   - Size each button for its importance.
   - Full width is allowed only for the screen's main choice (START RUN, TO CAMP on results). Everything else uses normal-width buttons.
3. **Leaving as a choice.** Where leaving is itself a meaningful choice, it gets a normal-size ghost or secondary button labelled with the consequence ("Skip", "Leave shop"), never a generic DONE or CLOSE. Where the × already covers it, drop the button.
4. **Forced modals** (a draft with no skip, the pre-boss camp, events, results) have **no ×**, no Esc and no backdrop dismiss. Only their explicit choice buttons close them.
5. **Confirmation dialogs keep an explicit cancel** (tech lead). Examples are the abandon confirm and the dev-menu channel switch. Cancelling is a real decision, and a destructive dialog must never offer only the destructive button plus a ×. These dialogs have no ×: the cancel (normal-width secondary) and the destructive or confirm button are the two exits, and Esc = cancel.
6. **Pause** is the one screen whose exit is its main action: RESUME (primary, full width) plus Esc, with no × (tech lead).

## 5. Icon style rules
1. **One family:** RhosGFX Vector Icon Pack Pro. Keyboard/mouse, emoji and hats come from the same artist and match its line weight. SVG only; PNGs are never referenced. All 400 icon ids and 25 input glyphs are in `ui/icons/icon_map.json`, and engineers swap by id through the foundation `Icons` registry, with the legacy `ui/icons/*.svg` as fallback.
2. **Two variants, by role:**
   - **Object / concept icons use `<Name> Outline.svg`:** full colour with a dark outline.
     - Covers currencies, stats, statuses, intents, runes, classes, biomes, tiles, potions, pets, passives, items, minigames.
     - `tint: null`. Caller tints are ignored, so the colour stays authored.
     - The outline makes them read on navy, on bright faces and over the 3D board.
   - **UI action glyphs use `<Name> Flat White.svg` + `tint: "palette:TEXT_DARK"`:** a monochrome glyph baked in label ink.
     - Covers close, back, arrows, chevrons, pause, play, speed, auto, info, help, check, plus, minus, home, gear, sound, music, menu, trash, download, skip, ui_size.
     - They share the button label's colour. On navy or ghost surfaces the caller passes `UiPalette.TEXT`, which the registry allows because it overrides the default tint.
   - **Die kinds** are the one tinted-object case: Flat White D6 × the `KIND` accent (hex in the map).
3. **Sizes (logical px):**

   | Context | Size |
   |---|---|
   | inline with body text | 28 |
   | chips and pills | 32 to 36 |
   | button icons | 52% of the face height (44 on 88 px buttons) |
   | round buttons | 46% of the size |
   | status row | 36 to 44 |
   | card art | 96 to 128 |
   | reward and hero moments | 160 |

   Below 24 px, prefer a Flat White glyph tinted with the semantic colour: an Outline at that size is mostly outline.
4. **On buttons and chips:**
   - The icon sits left of the label with a 10 px gap, and [icon + label] is centred as one unit (the current GameButton behaviour).
   - The icon's vertical centre is the face centre, not the control centre: face = height − lip.
   - Never place a self-contained "button" icon on a button face. The pack's `UI/X Button` is not used for close for this reason.
5. **No emoji or unicode glyphs as icons in UI chrome.** Replace these:
   - `★ KIT` → KIT chip with the `kit` icon
   - `★ Wild` → the `die_wild_face` icon
   - the BOO! star → `mech_boo`
   - `×` multipliers stay as text (typography, not icons)
6. **One icon, one meaning.** Crowns (currency) is no longer also the boss/throne/gilded icon:
   - boss → Horned Skull Red
   - throne → Crown 2 Purple
   - gilded → Coin 2 Gold
   - Sigils get their own purple Star Gem (not the generic star)
   - the curse padlock becomes Monkey's Paw, and the padlock means "locked"
7. **Coverage:** 400 icon ids and 25 input glyphs are mapped, and every path resolves to an existing file. The `missing` list (16 concepts) has fallbacks, summarised in §5.1.
   - The UI pack's bonus `[THANK YOU!] Icons` (same author, same purchase) are allowed as alternates. The map does not need them today: `Items/Chest/Chest 1..3` already provides full-colour chests.
   - **Rune glyphs on die faces** (about 20 px on the die body) use `rune_face_<id>`: Flat White × the `Runes.DEFS` colour. Wild uses GOLD, because its white would vanish on the ivory die (lead call on plan c). Everywhere else, runes use the full-colour `rune_<id>`.
   - **Combined icons** use the optional `badge` key: a second pack icon at the bottom-right corner, at 45% scale. **The foundation `Icons` registry must draw it** (the tech lead is telling the foundation). Until then these ids show only their base icon.
     - `mg_high_low`: Ladder + up arrow
     - `mg_plinko`: ball + down chevrons
     - `tile_moon_chest`: chest + moon
     - `passive_snake_eyes`: eye + die
   - **Thumbnail rule** (lead call on plan d): a pack icon replaces a *drawn* glyph. It never replaces a 3D render of the exact model (items, skins, pet portraits).
8. **Emoji and hats are bounded** (lead call on plan e).
   - Emoji are used only for:
     - the BOO! reaction (`cower` / `intent_cower`: Fearful face)
     - the minigame result-beat flavour face (GOLD Star-struck, SILVER Smiling face with sunglasses, BRONZE Grinning face, bust Face with spiral eyes, jackpot Money mouth face), at 64 px, popped once
   - Hats are used only as the Wardrobe hat-category icon (`wardrobe_hats`).
9. **Mechanic medallions** (`mech_*`) are the one tinted concept family: a Flat White glyph with `tint: palette:auto` (the mechanic colour), sitting on the mechanic-colour badge. Class icons stay full colour.
10. **Locked states:** icon entries accept an optional `saturation` key (0..1). Locked class chips, items and minigames pass 0 at call time and add a 18 px `lock` badge in the corner, instead of 0.7 alpha.

## 6. Input hints (desktop only)
**User decision (2026-09-30), relayed by the tech lead. It replaces the earlier badge placement.** There are no permanent keycap badges anywhere: not beside or on buttons, not under the dice, not on the HUD, pause menu or modals. Keys are taught in Settings → Controls. Every shortcut keeps working silently.

- **The one visual hint: a hover keycap.**
  - It appears on a button **only while the mouse hovers it**, and only in keyboard/mouse mode. It never shows after a touch event, and never on iOS or Android.
  - Size and placement: a small keycap (about 26 px tall on an 88 px button, 22 px on smaller ones) **inside the button's top-right corner**, inset 6 px from the face edge, clear of the label. It stays fully inside the face (§3.1).
  - **Round and icon-only buttons get no keycap.** A keycap inside the circle crowds the glyph, and one on the rim spills. Their shortcut goes in the tooltip instead, e.g. "Pause (Esc)".
  - It is drawn at **60% opacity**, fades in over 0.12 s on hover and out over 0.08 s on exit.
  - It is an overlay child with `mouse_filter = IGNORE`, so it changes neither the layout nor the hit rect.
  - Only buttons with a bound shortcut show it (see the table). Buttons without one show nothing.
  - Mockup: `mock_hover_keycap.png` shows normal and hovered states.
- **KeyGlyph widget** (plan e, still used by the hover keycap and the Controls list):
  - The keycap SVGs draw their letter as SVG `<text>`, which ThorVG drops. So the widget strips the `<text>` and draws the label itself in Lilita One (`#476475`, centred at 0.40 of the height because of the lip).
  - The ids, files and labels live in the `input_glyphs` section of `icon_map.json`: `svg`, `compact_svg`, `label`, `strip_text`.
  - `compact_svg` (the White set tinted TEXT) is kept for the Controls list at small sizes.
- **Mode detection:**
  - Keyboard/mouse mode = `OS.has_feature("pc")`, not `web_ios` / `web_android`, and the last input event was a keyboard or mouse event.
  - Any touch event switches to touch mode, which hides hover keycaps and uses the "Tap …" copy.

| Button | Hover keycap (the shortcut keeps working without it) |
|---|---|
| ROLL / GO / ATTACK / confirm move | `key_space` (Enter also works) |
| REROLL (board and combat) | `key_r` |
| Pause round button | `key_esc` (P also works) |
| Modal primary action / close X | `key_enter` / `key_esc` (the new UiModal bindings, added by area a) |
| Class select / carousel prev and next | `key_left` / `key_right` |
| Dice in the tray | **none.** 1–6 mark dice silently |
| AUTO pill | none; its tooltip says "Right-click or long-press for settings" |

- **Settings → Controls** (desktop only; area e builds it, area c hosts it in `settings_panel.gd`):
  - It lists every shortcut with its glyph (KeyGlyph at 34 px), built from the action table so it can't go stale. For example: `[SPACE] / [ENTER]  Roll · Move · Attack`, `[R]  Reroll`, `[1]–[6]  Mark dice`, `[ESC] / [P]  Pause`, and the minigame keys.
  - The pause menu has a "Controls" button that opens it. F1 also opens it, silently, with no badge.
- **Keyboard play in minigames** (lead: yes, where it is natural, via `scripted_input`): claw, wheel, fishing, shell (1–3), high-low (↑ / ↓ / C), plinko and shooter (← / → + Space). Grid games stay mouse-only.
- **Minigame instructions** may name keys **in text only** on desktop, with no badge art: "Space to drop", "← → to aim, Space to shoot", "Click to cast". Touch keeps "Tap …".
